# HTTP to Lambda

## Objective

- Understand the lifecycle from receiving an HTTP request through API Gateway to the execution of a Lambda function.

## Flow

```text
Client
  ↓ GET /visitors?id=2
API Gateway (HTTP API)
  ↓ builds a JSON event from the HTTP request
Lambda (proxy integration)
  ↓ returns { statusCode, headers, body }
API Gateway maps the result to an HTTP response
  ↓
Client receives a valid HTTP response
```

## Input

- Query parameter `id`; it acts as a simulated database identifier.

## Expected behavior

- API Gateway catches the request.
- API Gateway generates an event.
- The existing Lambda handles the event.
- A valid HTTP response is received.

| Case | Response |
| --- | --- |
| `GET /visitors?id=1` | `200` with the matching visitor |
| `GET /visitors` (no `id`) | `400` with a `MISSING_ID` error |
| `GET /visitors?id=999` | `404` with a `VISITOR_NOT_FOUND` error |

## Boundaries

- There is no real database; the data is mocked inside the function (`MOCK_VISITORS`).
- No Aurora.
- No RDS.
- No DynamoDB.

## Resources

- Lambda function: `lab-2-1-http-to-lambda`, Node.js 22.x runtime.
- API Gateway: HTTP API, route `GET /visitors`, stage `default`, proxy integration to the Lambda.

## Implementation steps (console)

### 1. Package the function

The handler uses ESM, so the file must be named `index.mjs` for the Node.js runtime to load it.

```bash
cd labs/api-gateway/http-to-lambda/src
zip function.zip index.mjs
```

### 2. Create the Lambda

- Author from scratch, name `lab-2-1-http-to-lambda`, runtime Node.js 22.x.
- Handler: `index.handler`.
- Upload `function.zip`.
- Keep the default execution role (basic CloudWatch Logs permissions).

### 3. Create the HTTP API

- API Gateway console → HTTP APIs → Build.
- Integration: the Lambda above, template HTTP route `GET /visitors`, payload 2.0.
- Stage: `default`, auto-deploy.
- The wizard automatically adds a Lambda resource policy granting `lambda:InvokeFunction` to `apigateway.amazonaws.com`. This is why the function can be invoked by the API without changing its execution role.

### 4. Invoke through HTTP

Replace `{invoke-url}` with the API's auto-generated URL:

```bash
curl -is {invoke-url}/visitors?id=1     # 200
curl -is {invoke-url}/visitors          # 400
curl -is {invoke-url}/visitors?id=999   # 404
```

## Event generated by API Gateway

Lambda does not receive the raw HTTP request. It receives a JSON event. With payload 2.0, the relevant fields are:

```json
{
  "version": "2.0",
  "routeKey": "GET /visitors",
  "rawPath": "/visitors",
  "rawQueryString": "id=1",
  "headers": { "...": "..." },
  "queryStringParameters": { "id": "1" },
  "requestContext": {
    "http": { "method": "GET", "path": "/visitors", "sourceIp": "...", "...": "..." },
    "requestId": "...",
    "domainName": "...",
    "time": "..."
  },
  "isBase64Encoded": false
}
```

With proxy integration, whatever the function returns must follow the `{ statusCode, headers, body }` shape; API Gateway maps it directly to the HTTP response. Returning a plain object (as in the Phase 1 labs) produces a `502` for the client.

## Inspect the logs

- Lambda logs: CloudWatch → Log groups → `/aws/lambda/lab-2-1-http-to-lambda`.
- Correlation: the response header `x-amzn-requestid` matches the `awsRequestId` used in each structured log line, so a single HTTP call can be traced end to end.

## Cost

- HTTP API: ~$1.00 per 1M requests, first 1M free per month. No idle cost (unlike REST API regional endpoints).
- Lambda: 1M free requests per month plus duration in GB-seconds; a cold start of this function is typically a few hundred ms.
- CloudWatch Logs ingestion for these volumes is negligible.

## Cleanup

After the lab is reviewed:

1. Delete the HTTP API (this also removes the Lambda resource-policy grant created by the wizard).
2. Delete the Lambda function (its log group is removed with it; verify no retained log group is left).

## Troubleshooting notes

To be completed during the "break and diagnose" part of the lab (task 2.3 will expand on this).

- `502 Bad Gateway`: the function returned a response that is not in the `{ statusCode, body }` proxy shape (typical when reusing a Phase 1 handler).
- `403 ` / `404` on an unknown path: the route does not exist in the stage; check the route key and that the stage was deployed.
